## 1. Purpose

The first step of creating a volunteer request. A member describes the opportunity, where it happens, and who to contact. The request is created at `draft` and the member is sent to MP-11 to add the individual roles. Structurally parallel to MP-07.

## 2. Entry and exit

**Arrives from:** MP-04.
**Leaves to:** MP-11 `/dashboard/volunteer/:id/add`, automatic redirect on save. Back control returns to MP-04.

## 3. Data

**Reads:** `organizations.name` for the session organization.

**Writes, in one transaction:** `volunteer_requests` at `status = 'draft'`, `org_id` from the session, `created_by` set to the acting user. `people`, or resolves an existing row by `lower(email)`, then sets `contact_person_id`.

**Functions called:** None.

**Never touches:** `submitted_at`, `approved_at`, `approved_by`, `archived_at`, `archived_reason`, `expires_on`. No `approval_events` row; the first event is written at MP-11 on submit.

### Field 8 is deviation one

Volunteer requests gain a deadline date. The current surface carries a deadline type with no date field to pair with it, which leaves the type selector describing a date that does not exist.

The control is lifted verbatim from MP-07 field 7 and behaves identically. This is the only addition to this surface and it is already approved; see `Handbook.md` section 4.2, deviation one. Its label matches MP-07's date picker label exactly.

## 6. Actions

**`[CAPTURE]` save button label**
- Enabled when: all required fields pass validation.
- Does: the write in section 3.
- Transaction boundary: the request and the contact person together or not at all.
- Emails queued: none.
- On success: redirect to MP-11 for the new request.
- On failure: nothing written, form retains every value, failure message renders.

**Back control**
- Navigates to MP-04. No write.

## 12. Error paths

| Failure | Rendered result |
|---|---|
| Contact email matches an existing person | Not an error. Attach the existing row |
| Single-word name in either name field | Succeeds. Stored as entered, no parsing |
| Image upload fails | `[CAPTURE]`. Default: save proceeds |
| Transaction fails partway | Nothing written. Every value retained |
| Deadline type is `date_specific` with no date | Blocked at the surface |

## 13. Out of scope for this surface

- Adding roles. MP-11.
- Submitting for approval. MP-11.
- Any status other than `draft`.
- Setting `expires_on`.

## 14. Acceptance

- A saved request lands at `status = 'draft'` with `org_id` from the session.
- Saving redirects to MP-11 for that request.
- The deadline date field is present, and behaves identically to MP-07's.
- First and last name land in two separate columns, never concatenated.
- A single-word name in either field succeeds.
- `description` and `details` land in their own columns and are not merged.
- No `approval_events` row and no email are produced here.
- The organization display field cannot influence which organization the request is created against.
- Field order, labels, and copy match the desktop screenshot, allowing for the added date field. Mobile matches the mobile screenshot.
