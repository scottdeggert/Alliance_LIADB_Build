## 1. Purpose

Where a member changes an existing item request and the items on it. Request-level fields, every item's editable fields, and the ability to add further items all live here, and all changes save together.

**Two deviations from the current surface, settled.** Claimed counts are display only (D1, deviation six) and the status selector never offers `active` to a member (D2, deviation seven). Both are described in section 5 and section 6.

### Conflict 1: claimed quantity is editable on the current surface

The surface being replaced allows a member to type over the claimed quantity. `Handbook.md` invariant 2 says `quantity_claimed` is written by `record_item_pledge()` and by nothing else, ever. These cannot both hold.

An editable claimed quantity means a member can silently desynchronize the counter from the pledge lines that back it, which makes the drift check fail, makes the public remaining count wrong, and makes it impossible to tell whether a donor's claim was recorded.

**Specified behavior: claimed is display only (D1).** `quantity_received` remains fully editable, because that is the organization's own record of what physically arrived and it is not a counter. Deviation six in `Handbook.md` section 4.2. It is invisible in layout, since the field stays on screen, and visible only in that one input becomes a read-only value.

If a member needs to correct a claimed quantity, that is a staff action, and there is no admin surface for it this week. Note it for phase two rather than building a back door.

### Conflict 2: reducing requested quantity below claimed

Lowering `quantity_requested` below the existing `quantity_claimed` produces an item that is over-claimed. `quantity_remaining` is generated with a `greatest(..., 0)` floor so it will not go negative, but the item is now in a state where more is promised than is wanted.

**Specified behavior:** block the save with a stated message naming the item and its claimed count. `[CAPTURE]` what the current surface does; it likely allows it silently.

## 6. Actions

**`[CAPTURE]` save button label**
- Enabled when: `[CAPTURE]` always, or only when something changed.
- Does: saves request-level fields and every item's fields in one transaction. Writes an `approval_events` row if and only if status changed, recording from and to status and the acting user.
- Transaction boundary: all changes across the request and every item succeed together or none do. A partial save that updated three items and failed on the fourth leaves the member unable to tell what stuck.
- Emails queued: `[CAPTURE]`. See the status conflict below.
- On success: success message, values persist, list re-renders with recomputed remaining.
- On failure: failure message, nothing written, every entered value retained.

**`[CAPTURE]` add item control**
- Enabled when: the add-item form passes validation.
- Does: inserts one `items` row with `quantity_claimed` and `quantity_received` at zero and the next `sort_order`.
- `[CAPTURE]` whether the new item is written immediately or held until save. This changes the transaction boundary and needs capturing rather than guessing.

**Back control**
- Navigates to MP-04. No write.

### Conflict 3: the status selector

The current surface offers a status selector including the value that makes a request public. `Handbook.md` section 12 puts that transition at ADMIN-02, staff only, and section 6 requires every transition to write an approval event. A member who can set their own request to `active` has bypassed approval entirely, which is the governance property the rebuild exists to establish.

**Specified behavior: the selector stays, its options narrow.** A member may move their request:

| From | To | Meaning |
|---|---|---|
| `draft` | `pending` | Submit for approval. Queues `staff_new_item_request` and `org_request_received`, same as MP-08 |
| `active` | `archived` | Close a request that is no longer needed. `archived_reason = 'manual'` |
| `archived` | `pending` | Reopen, returning through approval rather than straight to public |

A member may never set `active`. That option does not render for a member.

This is deviation seven (D2). `[CAPTURE]` the exact option labels currently shown, since the labels are bound even where the available options change.

## 12. Error paths

| Failure | Rendered result |
|---|---|
| Requested quantity lowered below claimed | Blocked, naming the item |
| Save transaction fails partway | Nothing written. Every entered value retained |
| Another member edited the same request concurrently | Last write wins (D8). No conflict UI this week |
| Status change to `pending` on a request with no items | Blocked |
| `:id` does not resolve | Same response as unauthorized |

## 13. Out of scope for this surface

- Approving a request or setting it to `active`. ADMIN-02.
- Writing `quantity_claimed` by any path.
- Deleting an item or a request. Requests archive; items cannot be removed (D7). If capture shows removal exists on the current surface, that becomes deviation ten with the same ruling. `[CAPTURE]` whether removal exists today.
- Setting `expires_on`.

## 14. Acceptance

- Editing and saving persists every changed field across the request and all its items.
- `quantity_claimed` cannot be changed from this surface by any means, including a tampered request payload.
- `quantity_received` can be changed and does not affect public availability.
- Remaining recomputes live while editing and always equals requested minus claimed, floored at zero.
- Lowering requested below claimed is blocked with a message naming the item.
- The status selector never offers `active` to a member.
- A status change writes exactly one `approval_events` row. A save with no status change writes none.
- Moving to `pending` queues both submission emails once.
- A failed save writes nothing and loses nothing typed.
- A member of another organization cannot load the surface.
- Field order, labels, and copy match the desktop screenshot. Mobile matches the mobile screenshot.
