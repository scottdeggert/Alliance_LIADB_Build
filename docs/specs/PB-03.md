## 1. Purpose

The public list of volunteer opportunities. Structurally parallel to PB-01, with one extra searchable field and a smaller list.

## 2. Entry and exit

**Arrives from:** the site navigation, social and email links, the legacy hub redirect, and PB-04 via back navigation.
**Leaves to:** PB-04 `/volunteer/:id`, by selecting a request card.

An unmatched legacy volunteer identifier lands here rather than on a 404.

## 3. Data

**Reads:** `volunteer_requests` where `status = 'active'`, joined to `organizations` where `kind = 'member_org'` and `status = 'approved'`. Fields: title, description, image, event location, and the organization's name and city.

**Writes:** Nothing.
**Functions called:** None.

**Never returns:** contact people, emails, phones, signup data, non-active requests, or unapproved organizations. Same shared public query helper as PB-01.

### Card contents

`[CAPTURE]` exact contents and arrangement. Expected: image, title, organization name, and location.

**Two location values exist on this side.** The request carries `event_location`, where volunteering happens, and the organization carries `city`. `[CAPTURE]` which the card displays, or whether both appear. They are not interchangeable: an organization based in one city can run an event in another, and a volunteer choosing where to spend a Saturday cares about the event location.

Card tokens in `Design.md`. The confirmed shadow was measured against twelve cards on this page specifically.

## 6. Actions

**Card selection**
- Navigates to PB-04 for that request. No write.

**Search input**
- Filters as the visitor types, debounced.
- Searches: request title, organization name, event location, and organization city. Four fields, one more than PB-01.
- `[CAPTURE]` the debounce interval, and confirm whether it matches PB-01's.
- No write, no navigation, no reload.

## 9. Empty states

Two, captured independently: no active volunteer requests at all, and search matched nothing.

The first is a live possibility here in a way it is not on PB-01. There are far fewer volunteer requests than item requests, so an empty list is a state a real visitor will hit. Its message should read as an invitation to check back or browse items rather than as a dead end. `[CAPTURE]` the current text; if it is bare, raise it with the captain.

## 12. Error paths

| Failure | Rendered result |
|---|---|
| Request query fails | A stated error. Never an empty list |
| A request's organization does not resolve | Exclude and log. No card with a missing organization name |

## 13. Out of scope for this surface

- Any signup action. That is PB-04.
- Filtering by population, date, or commitment level.
- Sorting controls.
- Counts or totals.

## 14. Acceptance

- Only `active` volunteer requests belonging to `approved` `member_org` organizations appear.
- Each card shows the correct organization's name and the captured location value.
- Search filters on all four fields and is case-insensitive.
- Debounce matches the captured interval.
- Both empty states render with their captured text.
- The response payload contains no contact or signup data.
- A failed query renders a stated error, not an empty list.
- Card shadow and radius match `Design.md`.
- Desktop and mobile match their screenshots.
