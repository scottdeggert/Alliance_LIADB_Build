## 1. Purpose

The first step of creating an item request. A member describes the need and who to contact about it. The request is created at `draft` and the member is sent straight to MP-08 to add the individual items. A request without items cannot be submitted, so this surface always hands off rather than completing anything.

## 2. Entry and exit

**Arrives from:** MP-04.
**Leaves to:** MP-08 `/dashboard/items/:id/add`, automatic redirect on save, carrying the new request's id. Back control returns to MP-04.

A member who abandons this form before saving creates nothing.

## 3. Data

**Reads:** `organizations.name` for the session organization, to display.

**Writes, in one transaction:** `item_requests` at `status = 'draft'`, `org_id` from the session, `created_by` set to the acting user. `people`, or resolves an existing row by `lower(email)`, for the request contact, then sets `contact_person_id`.

**Functions called:** None.

**Never touches:** `submitted_at`, `approved_at`, `approved_by`, `archived_at`, `archived_reason`. No status other than `draft`. No `approval_events` row; the request has not transitioned from anything yet, and its first event is written at MP-08 on submit.

## 6. Actions

**`[CAPTURE]` save button label**
- Enabled when: all required fields pass validation.
- Does: the write in section 3.
- Transaction boundary: the request and the contact person are written together or not at all.
- Emails queued: none. Nothing is submitted yet.
- On success: redirect to MP-08 for the new request.
- On failure: nothing written, form retains every value including the upload, failure message renders.

**Back control**
- Navigates to MP-04. No write.

## 7. Conditional behavior

This is the shared deadline control described in `Handbook.md` section 11. Identical on MP-09, MP-10, and MP-12. Build it once.

## 11. Authorization

Verify the session user holds an active membership, server-side. `org_id` on the new request comes from the session, never from field 11 or any client value.

## 12. Error paths

| Failure | Rendered result |
|---|---|
| Contact email matches an existing person | Not an error. Attach the existing row. One human, one row |
| Image upload fails | `[CAPTURE]` whether the save proceeds without it. Default: proceed, since a request can be approved without an image and staff routinely add one |
| Transaction fails partway | Nothing written. No orphan request with no contact, no orphan person with no request |
| Deadline type is `date_specific` with no date | Blocked at the surface. The database constraint also rejects it, but the member should never reach that |

## 13. Out of scope for this surface

- Adding items. MP-08.
- Submitting for approval. MP-08.
- Setting status to anything other than `draft`.
- Setting `expires_on`.

## 14. Acceptance

- A saved request lands at `status = 'draft'` with `org_id` from the session.
- Saving redirects to MP-08 for that request.
- The date picker appears only for `date_specific` and the date is required when it appears.
- No `approval_events` row and no email are produced by this surface.
- A contact email that already exists creates no duplicate person.
- First and last name land in two separate columns, never concatenated.
- A single-word name in either name field succeeds.
- The organization display field cannot influence which organization the request is created against. Verify by tampering.
- An abandoned form creates nothing.
- Field order, labels, and copy match the desktop screenshot. Mobile matches the mobile screenshot.
