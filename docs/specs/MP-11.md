## 1. Purpose

The second step of creating a volunteer request. A member adds the individual roles the request is asking volunteers to fill, then submits for staff approval. A request cannot be submitted with no roles. Structurally parallel to MP-08.

## 2. Entry and exit

**Arrives from:**
- MP-10, automatic redirect immediately after the request is created. Normal path.
- MP-12, if a link back exists. `[CAPTURE]`.
- Direct URL, for a request left at `draft`.

**Leaves to:** MP-04 on successful submit, and MP-04 via the back control.

Leaving without submitting leaves the request at `draft`, visible only to its own organization.

## 3. Data

**Reads:** `volunteer_requests` for `:id` (title, description, details, event_location, image_url, deadline_type, deadline_date, status, org_id), `volunteer_roles` for that request, `organizations.name`.

**Writes:** `volunteer_roles` on each add. `volunteer_requests.status` and `submitted_at` on submit. `approval_events` on submit. `email_log` on submit.

**Functions called:** None. The counter functions record signups, not roles.

**Never touches:** `volunteer_roles.quantity_interested`, `quantity_confirmed`, or `quantity_remaining`. New roles are created with the first two at their column default of zero; the third is generated and is never written.

## 6. Actions

**`[CAPTURE]` add role button label**
- Enabled when: required fields pass validation.
- Does: inserts one `volunteer_roles` row against `:id` with the entered values, interested and confirmed at zero, and the next `sort_order`.
- Transaction boundary: single insert.
- Emails queued: none.
- On success: the role appears in the list, the form clears, the success message renders.
- On failure: form retains values, error renders, nothing inserted.

**`[CAPTURE]` submit for approval button label**
- Enabled when: the request has at least one role. Disabled otherwise, from first render.
- Does: in one transaction, sets `volunteer_requests.status` to `pending`, sets `submitted_at`, writes an `approval_events` row from `draft` to `pending` with the acting user.
- Emails queued: `staff_new_volunteer_request` to both staff addresses, and `org_request_received` to the submitting member.
- On success: redirect to `/dashboard`.
- On failure: request stays at `draft`, failure shown, no partial submission.

**Back control**
- Navigates to MP-04. No write.

## 7. Conditional behavior

| Trigger | Result |
|---|---|
| Request has zero roles | Submit for approval disabled |
| Request has one or more roles | Submit for approval enabled |
| `deadline_type = 'date_specific'` | Deadline date displayed in the request summary |
| `deadline_type` is any other value | Deadline date hidden, not rendered blank |
| Role successfully added | Success message renders, form clears |

The deadline display on this surface only exists because volunteer requests now carry a deadline date, per deviation one. On a request created before that field existed the value is null and the row is hidden.

## 11. Authorization

Before any read or write, resolve the session user's active memberships and confirm one matches `volunteer_requests.org_id` for `:id`. The organization is never taken from the URL or a form field.

A member of another organization gets the same response as a request that does not exist.

An unauthenticated visitor is redirected to `/login`.

`[CAPTURE]` behavior when the request is not at `draft`. Default until confirmed: the surface loads read-only with the submit control absent.

## 12. Error paths

| Failure | Rendered result |
|---|---|
| Role insert fails | Error message, form values retained, nothing written |
| Submit transaction fails at any step | Request stays at `draft`, no approval event, no emails queued, failure shown |
| Email dispatch fails after a successful submit | The submit stands. Recorded in `email_log` as failed and surfaced in ADMIN-06. The member sees success, because their action succeeded |
| `:id` does not resolve | Same response as unauthorized |

## 13. Out of scope for this surface

- Editing or removing a role after adding it. MP-12.
- Any write to a quantity column other than `quantity_needed`.
- Approving the request. ADMIN-02.

## 14. Acceptance

- The surface renders the correct request's title, description, details, event location, and image.
- Deadline date is visible for a date-specific request and hidden otherwise.
- Submit is disabled on arrival with zero roles and enabled the moment the first role is added.
- Adding a role creates exactly one `volunteer_roles` row with interested and confirmed at zero.
- Roles render in the order added.
- Submitting sets status to `pending`, writes exactly one `approval_events` row, and queues exactly two email types.
- Submitting redirects to `/dashboard`.
- A member of another organization cannot load the surface and cannot tell whether the request exists.
- Field order, labels, and every message match the desktop screenshot. Mobile matches the mobile screenshot.
