## 1. Purpose

The entry point for organization members. A member arrives here, authenticates, and is routed to their organization's dashboard. The surface itself holds almost nothing: a single control that opens the authentication flow.

## 2. Entry and exit

**Arrives from:**
- The site navigation link that members use to reach the portal.
- Redirect from any authenticated route when no session exists.
- Legacy redirect from the old dashboard entry path.

**Leaves to:** MP-02 resolves the destination after successful authentication. This surface does not decide where the member goes. See MP-02 section 2.

An already-authenticated visitor who reaches `/login` is routed onward by MP-02 rather than being shown the login control again.

## 3. Data

**Reads:** `users`, `people` (via the auth layer only).
**Writes:** `users.last_login_at`. Session records, owned by the auth layer.
**Functions called:** None.
**Never touches:** `org_memberships`. This surface authenticates; it does not authorize. Membership resolution belongs to MP-02.

## 4. Layout regions

1. **Page content.** Heading and any instructional copy.
2. **Login control.** A single button that opens the authentication flow.

`[CAPTURE]` confirm whether the surface carries any additional content: a link for organizations that have not yet registered, help text, or a support contact.

## 5. Fields

None on the surface itself. Credential entry happens inside the authentication flow, which is provided by the auth layer rather than built here.

**Login method: magic link (D40, confirmed Aug 14).** The flow presents an email input and a sent-confirmation state. The login button label describes requesting a link, not entering a password. Tiffany reviewed the reasoning and did not object.

## 6. Actions

**`[CAPTURE]` login button label**
- Enabled when: always.
- Does: opens the authentication flow.
- Transaction boundary: none.
- Emails queued: one magic-link email.
- On success: control passes to MP-02.
- On failure: the authentication flow renders its own failure state. Do not build a second error surface here.

## 7. Conditional behavior

| Trigger | Result |
|---|---|
| Visitor already has a valid session | Routed per MP-02, login control not shown |
| Authentication succeeds | `users.last_login_at` set, control passes to MP-02 |

## 12. Error paths

| Failure | Rendered result |
|---|---|
| Authentication rejected | The auth layer's failure state. The message must not reveal whether the email exists in the system |
| Magic link expired or already used | A message offering to send a new one, not a dead end |
| Authenticated user has zero active memberships | Handled by MP-02, not here |

## 13. Out of scope for this surface

- Organization registration. That is MP-03.
- Any membership or permission check.
- Password reset flows beyond what the auth layer provides.

## 14. Acceptance

- The login control is visible and legible. Specifically, it is not white text on a white background; see the known bug in `Design.md`.
- Authenticating routes the member onward without a second click.
- An authenticated visitor hitting `/login` directly does not see the login control.
- A failed attempt does not disclose whether the email is registered.
- Desktop and mobile match their screenshots.
