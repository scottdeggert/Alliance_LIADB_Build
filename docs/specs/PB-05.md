## 1. Purpose

Where a member of the public opts in to the weekly email digest of new needs, and where they opt back out.

**The list is in scope this week. The send is not.** `Handbook.md` section 17 holds the scheduled digest send for phase two. Building the form and the table now means the list keeps growing and the existing subscribers survive the migration; the send is cheap to add later and the list is expensive to lose. Do not build a send job, a digest template, or a preview. The Thursday demo does not send to the live subscriber list; real cutover is the following week (D46). If the send job is not built for Thursday, showing the digest manually is acceptable.

**Bound status.** A subscribe form exists on the current site at its own path, so the form itself is bound and gets captured. The unsubscribe route is new, because the current list lives in a contacts system with its own unsubscribe mechanism that does not survive the move. Build it for clarity.

## 2. Entry and exit

**Arrives from:** the site navigation, links on the browse pages `[CAPTURE]` whether these exist, and the unsubscribe link in any future digest.

**Leaves to:** `[CAPTURE]` the post-submit destination. A confirmation state on the same surface is most likely.

`/unsubscribe/:token` is reached only from an emailed link.

## 3. Data

**Reads:** `digest_subscribers` by `lower(email)` on subscribe, and by `unsubscribe_token` on unsubscribe.

**Writes:** `digest_subscribers`. Inserts a new row on first subscribe, or updates `status` on resubscribe or unsubscribe.

**Functions called:** None.

**Never touches:** `people`. `digest_subscribers.person_id` is left null on signup (D27). Someone can subscribe without ever donating or volunteering. Do not create a `people` row from a subscription; an email address alone is not a person record, and creating one pollutes the identity spine with rows that have no name.

## 6. Actions

**`[CAPTURE]` subscribe button label**
- Enabled when: the email validates.
- Does: inserts a `digest_subscribers` row at `status = 'subscribed'`, or updates an existing row per section 12.
- Transaction boundary: single write.
- Emails queued: none (D28). There is no digest to confirm yet.
- On success: the confirmation in section 8.
- On failure: the message in section 8, the entered email retained.

**Unsubscribe, on link visit**
- Does: sets `status = 'unsubscribed'` and `unsubscribed_at` for the row matching the token.
- Renders confirmation. No further action required from the person.

## 11. Authorization

None. Both routes are public.

The unsubscribe token is the authorization. It is a uuid, it is unguessable, and it is the only thing needed to unsubscribe, deliberately: a person unsubscribing should never have to log in, remember anything, or click twice.

The subscribe route is a public write endpoint and is rate limited by IP with a per-endpoint ceiling (D10).

## 12. Error paths

| Failure | Rendered result |
|---|---|
| Email is already subscribed | Not an error. Show the normal success message. Never say the address is already on the list; that discloses membership of the list to anyone who guesses an address |
| Email exists at `unsubscribed` | Set back to `subscribed`, normal success message |
| Email exists at `bounced` | Set to `subscribed` (D29). A person actively re-entering their address beats a historical bounce |
| Unique index rejects the insert | Handle before the database does, per the rows above |
| Token not found or already used | The message in section 8. Not a 404, not an error page. A second click on an unsubscribe link is normal behavior |
| Write fails | Failure message, email retained |

The first row is the one to get right. A message reading that an address is already subscribed lets anyone test whether a given person is on the list.

## 13. Out of scope for this surface

- The digest send job, in any form. Phase two. Eligibility, when that spec is written: `approved_at` both non-null and within the lookback window (D43). Historical migrated rows are left null; anything that becomes active afterward must get a real timestamp (D48). Thursday demo does not send to this list (D46).
- A digest email template.
- Preferences, frequency options, or topic selection.
- Any confirmation or double opt-in flow, unless the captain adds one.
- Creating a `people` row.

## 14. Acceptance

- A new email creates exactly one `digest_subscribers` row at `subscribed`, with a generated token.
- Subscribing an already-subscribed address shows the normal success message and creates no second row.
- Subscribing a previously unsubscribed address returns it to `subscribed`.
- Email matching is case-insensitive throughout.
- No `people` row is created by any path on this surface.
- The unsubscribe link works on first click with no login and no second confirmation.
- A reused or unknown token renders a plain message, not an error page.
- No response discloses whether a given address is on the list.
- Desktop and mobile match their screenshots.
