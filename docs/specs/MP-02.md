## 1. Purpose

Site-wide navigation behavior and the routing logic that decides where an authenticated member lands. This is not a page. It is the shared layer every other surface renders inside, and it owns the single most failure-prone operation in the system: resolving which organization a logged-in person belongs to.

## 2. Entry and exit

**Runs on:** every page load, authenticated or not.

**Post-authentication routing.** Query `org_memberships` for the session user where `status = 'active'`. Branch on the count:

| Active memberships | Destination |
|---|---|
| 0 | Pending-approval message. No dashboard access, no navigation to member routes |
| 1 | `/dashboard`, scoped to that organization |
| 2 or more | Organization chooser, then `/dashboard` scoped to the selection |

The selection persists in the session and a visible switcher lets the member change it without logging out.

**Logout:** returns to the public site home.

## 3. Data

**Reads:** `org_memberships` (org_id, user_id, role, status), `organizations` (id, name, kind), session.
**Writes:** the selected organization on the session. Nothing in the database.
**Functions called:** None.
**Never touches:** any request, item, or supporter table.

## 4. Layout regions

1. **Navigation bar**, present on every page.
2. **Dashboard control**, conditionally present within the navigation.
3. **Organization switcher**, conditionally present, only for members with more than one active membership.
4. **Pending-approval message**, rendered in place of dashboard content for a member with zero active memberships.

## 5. Fields

Organization switcher, when present:

| # | Label (verbatim) | Control | Required | Binds to | Validation |
|---|---|---|---|---|---|
| 1 | `[CAPTURE]` | Select | Yes | Session-scoped org selection | Value must be an org the user holds an active membership in |

The switcher lists only organizations where the membership is `active`. It never lists an organization from a `pending` or `removed` membership.

## 6. Actions

**Dashboard control**
- Enabled when: the session has one or more active memberships.
- Does: resolves the organization per section 2 and navigates to `/dashboard`.
- Emails queued: none.
- On failure: see section 12.

**Organization switcher**
- Enabled when: two or more active memberships.
- Does: sets the session's selected organization and reloads the current dashboard route scoped to it.
- On failure: the previous selection stands.

**Logout**
- Does: ends the session and returns to the public site home.

## 7. Conditional behavior

| Trigger | Result |
|---|---|
| No session | Dashboard control hidden |
| Session with one or more active memberships | Dashboard control visible |
| Session with exactly one active membership | No organization switcher rendered |
| Session with two or more active memberships | Organization switcher visible in the navigation |
| Session with zero active memberships | Pending-approval message, no dashboard access |

The switcher is not visible to any member of a single organization, which is every current member. It exists because the data model can now express a person holding two memberships, and the alternative is a redirect that silently picks one.

## 11. Authorization

This layer performs the membership query that every organization-scoped route depends on. It does not replace those routes' own checks. Each route re-verifies membership server-side before its query, per `Handbook.md` section 5. A session-held organization selection is a convenience, never a permission.

## 12. Error paths

| Failure | Rendered result |
|---|---|
| Membership query fails | A stated error. Never a silent fallback to some default organization |
| Session references an organization the member no longer has an active membership in, for example after removal mid-session | Clear the selection and re-resolve per section 2. If that yields zero, show the pending-approval message |
| Authenticated user has no `people` row | This is a data defect, not a user error. Log it and show a stated error. Do not create records to paper over it |

The second row is the one that matters operationally: a member removed at MP-05 while logged in must lose access on their next request, not at their next login.

## 13. Out of scope for this surface

- Authentication itself. That is MP-01.
- The dashboard's contents. That is MP-04.
- Any public-site navigation behavior outside the portal.

## 14. Acceptance

- Dashboard control appears only when a session exists.
- A member with exactly one active membership reaches `/dashboard` directly after authenticating, with no intermediate screen.
- A member with two active memberships sees the chooser, selects, lands on the correct organization's dashboard, and can switch.
- A member with zero active memberships sees the pending message and cannot reach any dashboard route by typing its URL.
- Membership resolution performs no string comparison against organization names anywhere in the path. This is invariant 1 in `Handbook.md` section 6 and it is the root cause of the fault class being eliminated.
- A member removed mid-session loses access on their next request.
- Navigation matches the screenshots in both states, desktop and mobile.
